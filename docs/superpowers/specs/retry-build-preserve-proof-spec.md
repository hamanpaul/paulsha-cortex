# retry-build 在 launch 前失敗時保留 slice 既有 proof 規格

## Requirements

對應 [#479](https://github.com/hamanpaul/paulsha-cortex/issues/479) 的殘項。票面主缺陷（`slice-action retry-build` 沒把 `launcher_factory` 傳進 `dispatch_ready`）已由 `6b4160f6`（PR #941）修掉，本項不重做；本項只修票面驗收「dispatch setup 在 launch 前失敗時，保留 coherent 的先前恢復狀態，不清 proof 欄位、不把 reason 換成 `missing-slice-proof`」。

名詞：
- **恢復態 slice**：本次 `dispatch_ready` 迭代開始、任何 registry 寫入之前，registry 已有此 slice row 且 `state ∈ {needs_human, failed}`。
- **launch 前失敗**：`dispatch_ready` 單一 slice 的 try 區塊內、`pin_dispatch_inputs` 成功之後、`active_launcher.launch(...)` 回傳之前拋出的任何例外（`pin_dispatch_inputs` 本身失敗不屬此類，一律依 R5 g），含 identity 查找／`launcher_factory` 缺席或拋錯、`_record_pending_slice`、`_read_pinned_spec_body`／`build_dispatch_prompt`、`_resolve_target_base_sha`、`_launcher_worktree`、`_record_launching_job`、`_mark_slice_building`、`limiter.admit`，以及 `launch()` 本身拋錯。

1. **R1 恢復態 slice 的 proof 原樣保留**：恢復態 slice 發生 launch 前失敗後，slice row 的 `spec`、`plan`、`target_branch`、`target_remote`、`verification`、`dispatch_base`、`builder_job_id`、`reviewer_job_id`、`candidate`、`current_verification_evidence_hash`、`current_evidence_refs`、`current_evaluation_refs`、`state`、`gate_state` 與迭代開始前逐欄相等；`evidence_history`、`evaluation_history` 不增不減。`failed` 維持 `failed`，不得改寫成 `needs_human`。
2. **R2 失敗照舊可見、可用動作不變**：R1 情境下 `dispatch_ready` 照舊把該 slice 收進 `DispatchReadyError`（錯誤訊息不變，unknown identity 仍列出可用 candidates），`apply_slice_action(retry-build)` 照舊往外拋、不記 `operator-retry-build` ok；slice `actions` 恰好新增一筆 `action == "dispatch-failed"`、`actor == "manager"` 的紀錄（其 `state`／`gate_state` 為保留後的值）；這筆稽核紀錄與現行 `_mark_slice_needs_human`（`autonomy.py:1145-1154`）同為 best-effort：`record_action` 本身拋錯時只記 log、不重試、不觸發 R4 退路（R4 退路只涵蓋還原寫入），此時 `actions` 不增，R1 其餘欄位仍須成立；`manager.allowed_slice_actions` 回傳與失敗前相同的清單（needs_human＋合法 candidate 仍含 `retry-build`；`failed` 且 `slice_repin_eligible` 仍含 `retry-build`）。修正原因後再次 `retry-build` 成功時，行為與現行成功路徑逐字相同（repin 清 proof、綁新 builder job、`state=building`、`gate_state=pending`）。
3. **R3 從未 launch 的新 attempt 只供稽核**：`launch()` 拋錯時 `_record_launching_job` 已建立的新 job row 維持現行 `_fail_launching_job` 結果（`status == "failed"`、`runtime_diagnostic.reason == "launch-failed"`），不刪除、不改寫。`complete_tick` 對同時滿足「非 review kind、非 workflow lane（`workflow_run_id is None`）、`status == "failed"`、`runtime_diagnostic.reason == "launch-failed"`、registry 有此 slice row 且其 `builder_job_id != job_id`」的 job 直接跳過：不寫 handoff manifest、不寫 evidence、不改 slice、不進 `completed`／`errors`、不觸發 verification runner。此條件不區分 launch-failed 的來源：除本項 spawn 失敗外，也涵蓋 `_attach_launch_handle` 失敗（`launch()` 已回傳，`autonomy.py:822` 拋錯後 `:835-842` 同樣標 `launch-failed`）與 `Dispatcher.poll_headless_done` 的 launch handle 缺失——只要它們已不是 slice 的 `builder_job_id`。這些 job 已是 terminal `failed`、不再持有 slice；現行對它們只會走 `status == "failed"` 分支（`manager.py:2559-2585`）寫一份覆蓋現任 owner manifest 的 `builder-failed-*` manifest，且 `slice_row is None` 不寫 slice；launch-failed 分類不記 executor backoff，slice lane job 沒有 `workflow_card`、不產生 skill ledger 事件，跳過不會丟失任何狀態。仍綁定者照舊處理（R5 e／f）。因此 R1 之後連跑兩次 `complete_tick`，該 slice 的 handoff manifest bytes 不變（`job_id` 仍是舊 job）、新 job 不寫 `builder-failed-launch_failed` manifest、舊 builder／reviewer job 不因解綁落 `missing-slice-proof`、也不被重新 finalize（`actions`／`evidence_history`／`evaluation_history` 長度不變）。
4. **R4 還原有前置條件與退路**：只有「本次迭代的 repin 已生效且尚未 launch」才執行還原；執行前重讀 row，還原會覆寫的每個欄位都必須仍是本次迭代寫入後的形狀——`spec.hash`／`plan.hash`／`verification.hash`／`target_branch`／`target_remote` 等於本次 pinned inputs；`dispatch_base` 等於本次迭代最後寫入的值；`builder_job_id ∈ {None, 本次新建的 job_id}`；`reviewer_job_id is None`、`candidate is None`、`current_evidence_refs == []`、`current_evaluation_refs == []`、`current_verification_evidence_hash is None`、`gate_state == "pending"`；`state` 等於快照值，或為 `building` 且 `builder_job_id` 是本次 job；`actions`、`evidence_history`、`evaluation_history` 長度與快照相同（本次迭代在還原前不記 action，長度變了代表他人已寫入）。前置條件不成立、或還原中任一 registry 寫入拋錯 → 退回現行行為（`_mark_slice_needs_human`），不得覆寫他人已寫入的變更。本次迭代若尚未 repin（例如 identity 檢查、`_record_pending_slice` 本身失敗），恢復態 slice 不做任何 repin 或還原，只記 R2 的 `dispatch-failed`。
5. **R5 其他路徑行為不變**：(a) 首次派工（registry 無此 slice row）launch 前失敗 → 照舊補建 slice 後落 `needs_human`，`dispatch_base` 為 early branch head（#333-1）；(b) 既有 row 為 `pending` 或其他非恢復態 → 照舊 repin＋`_mark_slice_needs_human`；(c) launch 成功 → 照舊 repin 清 proof、綁新 job；(d) executor backoff skip 照舊不寫 slice／worktree／job；(e) `launch()` 已回傳 handle、之後才失敗（`_attach_launch_handle` 拋錯）→ 維持現行處理；(f) 仍綁在 slice 上的 launch-failed job（例如首次派工 spawn 失敗）照舊由 `complete_tick` 落 `failed`、`gate_reason` 為 `builder-failed-*`；(g) `pin_dispatch_inputs` 本身失敗（尚無 pinned inputs）照舊不寫任何 slice 欄位或 action。
6. **R6 測試**：新增 `tests/test_retry_build_preserve_proof.py` RED→GREEN，涵蓋 design D7 矩陣每一列；既有 `tests/test_coordinator_operator_actions.py`、`tests/test_executor_backoff_slice_lane.py`、`tests/test_slice_executor_model.py`、`tests/test_pinned_spec_delivery_503.py`、`tests/test_fix_slice_failed_deadend.py`、`tests/test_persona_phase4_fanout_autonomy.py`、`tests/test_pre_candidate_recovery.py`、`tests/test_coordinator_dispatch_discipline_e2e.py` 原斷言保留、全綠。

## Boundary

Production 只改 `paulsha_cortex/coordinator/autonomy.py`（`dispatch_ready` 的恢復態快照、`launched` 旗標、except 分支，新增還原／收尾 helper）與 `paulsha_cortex/coordinator/manager.py`（`complete_tick` build 分支的 unbound launch-failed skip）。不改 `registry.py`（不新增 writer、不改 `repin_slice`／`update_slice` 語意；recovery receipt、revision、attempt supersession 屬 #862／#497）；不改 `manager_daemon.py`、`cli.py`、`porcelain/recover.py`（`launcher_factory` 接線已由 #941 完成）；不改 `apply_slice_action` 的成功與錯誤回傳形狀。

不處理：一般 superseded terminal job 重播與 manifest 單槽 ping-pong（#481／#497）；`recover-pre-candidate` 清綁定（#497）；retry-build 對既有 candidate worktree／branch 的 provision 語意（`GitWorktreeCreator.create` 拒絕 `worktree target already exists`／`existing worktree branch has commits outside requested base` 本身）；verified slice 退回（#502）；needs_human 且無 manifest 時 tick 重複嘗試派工；worktree／job row 回收；還原中途崩潰的原子性（中途崩潰退化為現行結果，不宣稱原子）。

## Evidence

- #479 本文與 2026-08-12 五則 recurrence：`slice-action ... retry-build` 失敗後 `builder_job_id`／`reviewer_job_id`／`candidate` 被清空、spec 被 repin 成 recovery-context hash、`dispatch_base` 變成前一個 candidate，reason 變 `missing-slice-proof`，只剩 `recover-pre-candidate`／`abandon`，candidate 需 operator 另存 archive ref 保護。
- main `7fa4716b`：`autonomy.dispatch_ready` 在 identity 檢查（`autonomy.py:680-700`）之後、prompt／base_sha／worktree（`:753-771`）之前就呼叫 `_record_pending_slice`（`:740-746`）；既有 row 走 `registry.repin_slice`（`autonomy.py:1105`），清 `builder_job_id`／`reviewer_job_id`／`candidate`／`current_*`（`registry.py:1555-1564`）。except 分支對 `not slice_recorded` 仍補呼叫 `_record_pending_slice`（`autonomy.py:825-834`），連 identity 階段（repin 前）的失敗也會 repin；最後 `_mark_slice_needs_human`（`:843-844`）把 `failed` 改寫成 `needs_human`。
- `manager.allowed_slice_actions`（`manager.py:646-670`）對 needs_human 且 candidate 非合法 SHA 只回 `recover-pre-candidate`／`abandon`。repin 解綁後，`complete_tick` 對舊 job 的處理依 kind／status 而異：review job `_slice_for_reviewer_job` 回 None 落 `missing-slice-proof`（`:2472`、`:2497-2503`）；exited build job `_slice_for_job` 回 None（`:2474`）落 `missing-slice-proof`（`:2592-2605`）；failed build job 先進 `status == "failed"` 分支寫 `builder-failed-*` manifest、不寫 slice（`:2559-2585`）。manifest 冪等只比單槽 `job_id`（`:2468`、`:187-199`），故多個未綁定 terminal job 會輪流覆寫同一份 manifest。
