- **#716（選項 B 的前置）：出口網路管制落地——`IPAddressDeny=any` ＋ 專屬 loopback 位址上的主機名白名單 proxy。** B 的裁決逐字帶著一句「出口網路不補就不要採 B」，因此順序是先補管制、再關內層，中間不得存在「沒有內層沙箱且出口全開」的窗口。**起因**（0819 實機，builder 真實加固面複本、`unit_replica_properties()` 全量導出 42 條 property）：`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` 之下 TCP 443 `OUTBOUND-OK ('1.1.1.1', 443)`、DNS rc=0、`curl https://api.openai.com/v1/models` → `http=401`、`busctl --system list` rc=0；合併「job 讀得到自己的 `auth.json`」（兩層都不擋，而且**不該**擋——R-6 取捨：token 過期必須 refresh 得回來）⇒ 一次跑完逐字 `CREDS-READABLE / EGRESS-OPEN`，**模型跑的任意命令可讀出自己的 token 並外傳，一條命令兩步**。
- **形態不是位址白名單**：`api.openai.com` 解到 Cloudflare（`162.159.140.245`／`172.66.0.243`），CIDR 會漂且同一組位址上有無數其他站點 ⇒ 位址級表達不出「只連得到模型 API」。改為兩層：**核心層**（job unit 的 `IPAddressDeny=any` ＋ `IPAddressAllow=<proxy>/32`，位址級、核心強制，模型命令 `env -u HTTPS_PROXY` 繞不過）＋ **可用性層**（root-owned unit 上的 `Environment=HTTPS_PROXY=`，大小寫兩套 ＋ `NO_PROXY=` 清空）。
- **codex 自帶的 managed proxy 查證後不採用**：`codex_network_proxy` 確實存在（MITM、`allowed_domains`／`denied_domains`、`/etc/codex/managed_config.toml`），但功能描述逐字是 “Apply network proxy restrictions to **sandboxed sessions** that already have network access.”——它套在**內層沙箱**上，而 B 的前提就是關掉那一層；`codex features list` 逐字 `network_proxy experimental false`；強制手段是把 `HTTP_PROXY`／`NPM_CONFIG_*`／`PIP_PROXY`… 注入子行程環境，沒有內層沙箱時 `unset` 一下就繞過。**結構上不成立。**
- **`respect_system_proxy` 不是前提（實測否證）**：`codex features list` 逐字 `respect_system_proxy under development false`，但旗標維持預設時 `HTTPS_PROXY=… codex cloud list` 仍在 proxy log 留下 `CONNECT chatgpt.com:443`。三支 executor **都吃** proxy env（codex／claude／agy 各自的 `CONNECT` 逐字記在 `EXECUTOR_TOOLS` 的 `api_hosts` evidence 上）⇒ 本形態**不需要任何 argv／feature flag 變更**。
- **新增 `cortex-egress-proxy.service`**（`permgen.build_egress_proxy_unit()` 機械產生）：`User=cortex-egress`——**不是**任何 job 帳號、不是 Manager、無 root；**零 `ReadWritePaths`**（白名單來自部署樹裡的程式碼，log 走 journal）；與 job unit 共用同一張 `_HARDENING` 與圍堵表。本體是 `paulsha_cortex/trust_root/egress_proxy.py`（stdlib-only CONNECT proxy）：exact-match 主機名、只放 443、拒絕明文 forward 與 IP 字面量、解析結果落在非全域位址一律拒（DNS rebinding 防線）。
- **白名單是宣告式的單一來源**：`ToolchainProgram.api_hosts` → `permgen.egress_allowlist()`，unit 註解、`cortex egress-proxy --check`、`trust_root egress-allowlist` 與 proxy 執行期讀的**是同一支函式**。每一格帶逐字量測 evidence 與 `measured` 旗標，未量測的格子由 `unmeasured_egress_hosts()` 列出來——**「量過」與「沒量過」是兩個看得出來的值**（#714 的原型錯誤是一格空白同時代表「沒有」與「還沒量」）。
- **proxy 綁專屬 loopback 位址而非 `127.0.0.1`**：`IPAddressAllow=` 沒有埠的概念。0819 實測 `IPAddressAllow=127.0.0.1/32` 之下 job `REACH-OK docker-tcp-2375`——**未認證的 docker daemon TCP API ＝ 宿主 root**；改綁 `127.0.7.16` 後同一條變 `REACH-BLOCKED … TimeoutError`。`EgressProxy.__post_init__` 對 `127.0.0.1` 與非 loopback 位址直接拒絕。
- **shim 那一層一併補上（少了它整件事是無聲的 no-op）**：shim 以 `os.execvpe` **整份換掉**環境，unit 的 `Environment=` 只到得了 shim（與 `HOME` 同一個機制）。`job_shim._apply_egress_proxy_env()` 把 root-owned unit 上的宣告帶進 job 的環境，名字集合與 `permgen.EGRESS_PROXY_ENV_NAMES` 由契約測試雙向釘死；空字串（`NO_PROXY=`）是有意義的值，用 `in` 判斷而非 truthiness。
- **半套的出口管制在產生複本的那一刻就紅**：`unit_replica_properties()` 新增 `_assert_egress_pair_intact()`——落檔的 unit 只有 `IPAddressDeny` 沒有 `HTTPS_PROXY`（症狀是「模型 API 逾時」）或反之（unit 讀起來像關上的、實際全開）一律 `UnitReplicaDriftError`。它是 runbook 每一條驗證的入口，因此同時保護之後的每一條。
- **圍堵條款（六份 job unit ＋ proxy unit）**：`InaccessiblePaths=-/run/dbus -/run/docker.sock`（已量到生效：`busctl` 由 rc=0／31 列變逐字 `Failed to connect to bus: Permission denied`；D-Bus 提權那一格從「唯一防線在 polkit」變成兩道）、`TasksMax=512`（已量到生效：`TasksMax=32` 下 `FORK-STOP at 31`）、`MemoryMax=25%` **＋ `MemorySwapMax=0`**（**必須成對**：只設 `MemoryMax=64M` 時 200MB 配置仍 `ALLOC-OK`，補上 swap 上限後 rc=1；成對性由結構測試釘住）。
- **`SocketBindDeny=any` 重量之後刻意不加**：systemd 接受（rc=0），但 `bind(('0.0.0.0',18081))`／`bind(('127.0.0.1',18082))` 皆逐字 `BIND-OK`，與對照組相同；成因是本機 `systemctl --version` 逐字 `-BPF_FRAMEWORK`（`IPAddressDeny` 走的是不需要 libbpf 的路徑，因此**有**生效）。它與同因未量到的 `RestrictFileSystems=` 一起登記在 `permgen.HARDENING_DEFERRED`，逐字理由印進每一份 unit 的註解——**不靜默放進去當安慰劑**，測試斷言它不以指令形式出現、但理由必須留在 unit 上。
- **適用面**：builder ＋ reviewer／planner 的四份 unit 受出口管制（reviewer 的 read-only lane 實測 `chatgpt http=405` 不受影響）；**gate 的兩份明示不受管制**並附逐字理由（gate 跑 operator 宣告的命令、可能需要套件來源，本票一條都沒量；gate 帳號不持有任何模型憑證）；Manager／monitor 兩份**完全不動**（Manager 的 `systemctl start` 走 D-Bus，封它等於切斷派工）。涵蓋面由 `_validate_egress_coverage()` 在 import 時強制——新增 job principal 而沒有做出「要不要管出口」的決定時模組載不起來。
- **真實 `codex exec` 驗收**（唯一一次，`-s read-only` ＋ legacy landlock）：在 `IPAddressDeny=any` ＋ `IPAddressAllow=<proxy>/32` ＋ DNS 完全不通之下 rc=0、模型逐字回 `PSC716-EGRESS-OK`、10,659 tokens；proxy log 逐字 `CONNECT chatgpt.com:443` ALLOW ×17、`CONNECT ab.chatgpt.com:443` **DENY**（遙測端點被拒，codex 照常完成 turn ⇒ exact match 就夠，不需要 wildcard）。
- **未量到（不要當成已解）**：`auth.openai.com`／`api.github.com`／`api.githubcopilot.com`／`accounts.google.com` 四格未實機看到被請求（`--check` 會標）；`agy` 的量測走到互動式登入就逾時，**它在已登入狀態下真正的模型 API 主機沒有被量到**；builder 的 `workspace-write` 形態在 B 的 argv 半落地之前跑不起來，因此**沒有**在出口管制下量過寫入形態。
