# #842 execution qualification lifecycle

新增 profile-bound qualification candidate、confirmed operator approval CLI、content-addressed human receipt store 與 Manager-only id/digest allowlist。Receipt 綁定 candidate、report/profile digest、role/coverage、policy revision、actor/reviewer、reason、reviewed_at 與 expiry；偽造檔、未登記 id、digest 不符均不能發布或通過 roster query。Trust Root/permgen 明列 operator/Manager 寫入與 job 隔離；`execution-qualification` 容器本身獨立登記為資產，讓子資產各自有明確的 managed parent，install-plan 才能同時承接既有四項 candidates/receipts/roster/index 與新增兩項 operator receipt 的 traverse ACL。generation、review 與 expiry 比較使用 timezone-aware datetime；test-only receipts 不授予 sized-dispatch enforce 下的 live qualification。

對抗審查第三輪修法：operator receipt 的雜湊與內容現在綁定核發當下的 binding generation，重跑完全相同參數的 `qualification approve` 不會再拿回撤銷前的舊人類 receipt；approve／revoke 皆會推進 generation，撤銷後任何綁在舊世代的 receipt（含撤銷前的核可 receipt）都無法再把 binding 翻回 approved，只有綁新世代的新 receipt 才可核可。`review_candidate`／`revoke_qualification` 取得 lifecycle lock 後、寫入前重新量測時間並複查 reviewed/expires，避免他 process 持鎖到 receipt 過期後才放行卻仍以取鎖前的舊時間戳通過。Q07 兩 process 競爭測試改走真正的 operator receipt store（multiprocessing + barrier 對 live publish/revoke），並以全新 store 實例驗證新消費者不會看到缺有效人類 receipt 的 approved row。

對抗審查第四輪修法（BLOCKER 1）：發布的 Trust Root ACL 下 `operator-receipt-index.json` writers/readers 都是 Manager-only，但 `issue_operator_receipt()` 原本自己寫這個檔案——operator 帳號與 Manager 帳號分離時寫不進去，live receipt 發不出來，approve／revoke 完全無法執行。修法後 operator 路徑只寫自己有權限的 `operator-receipts/` immutable receipt 檔（atomic、content-addressed、同 id 不同內容拒絕覆寫），不再嘗試寫入該 Manager-only index；讀取端（`_read_operator_receipt`）改為「讀得到、對得上就多一層佐證，讀不到（不存在／權限不足）或查無此筆就退回單靠 receipt 檔本身 content-addressed 自證」，operator 自己核發、尚未被登記的 receipt 不再被誤判為「未登記」而擋下發布或 roster 查詢。新增測試以真實檔案權限（chmod 0o000）模擬 operator／Manager 帳號分離，證明 CLI 的 approve／revoke 在該 index 完全不可讀寫的情況下仍能走完全程，且 Manager 端 `qualification_status`／`read_roster` 查詢結果正確。
