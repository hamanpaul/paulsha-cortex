- RC qualification 新增 `legacy-adoption` profile（#1122，PR-5）：在同一個 disposable reference image 容器內布置 Phase 2b 形狀的舊主機並走完 installer 的 legacy adoption，release 含 installer 或 qualification 變更時 release preflight 必須看到 exact SHA 的通過 run。
  - **fixture**（`qualification/legacy_fixture.json`＋`legacy_fixture.py`）：五個 cortex 帳號用非 release 預設、uid≠gid 的 id（egress home 為不存在的 `/srv/cortex-egress`）、實體 `/opt/cortex/venv`、未版本化 toolchain 與超過 hash 上限的 sparse binary、9 個手工 unit＋installer 不產生的 #568 reviewer drop-in＋`*.wants` 連結、polkit rule、帶 ACL／mask／default ACL 的 state、plan 未宣告的 state 頂層項目、受管目錄內未列管子目錄與 `*.tmp`／`*.bak` 殘留、兩個 worktree pool、帶 branch 與 worktree 的非 canonical source repo（`example.invalid` origin）、`/opt/cortex/etc` 舊設定與只含 `legacy-fixture-secret-*` 假值的 credential 檔。manifest 驗證拒收 release id、`/home/` 路徑、重複路徑、缺父目錄、未知 owner；布置只在有容器標記的 root 環境執行，另有 rootless 模式供單元測試。`expected.quarantine` 釘住 plan 應 quarantine 的 49 個物件。
  - **harness**（`qualification/legacy_adoption.py`，容器內 root）：布置 fixture 並啟動舊服務 → `legacy inventory`（census 必須 stable，no-overwrite 發布到 `/var/lib/cortex-installer/legacy/<sha>.json`）→ 持久化 host overlay → `plan --host-overlay --legacy-inventory`（CLI 回報、檔案 digest、`plan_sha256` 重算三方一致，quarantine 集合必須等於 fixture 預期）→ 停舊服務 → `apply --legacy-inventory`（每個 quarantine destination 持有原 inode、adopted 樣本 inode 與 bytes 不變）→ `rollback`（`legacy_restored=true`、`restore_safe=true`、無 retained、每個物件以相同 dev／ino 回到原路徑、quarantine destination 清空、三個 unit `NeedDaemonReload=no`）→ 重啟再停舊服務 → 再 apply → 以 quarantine 內的假 credential 重新匯入 → `activate` → `verify`。rollback 證明刻意排在 credential 匯入與 activate 之前：新服務啟動後寫入的 runtime state 依設計會讓 rollback 成為 rollback-blocked。每步寫進 `legacy-adoption.json`，credential 連 digest 都不進 evidence。
  - **driver／validate／schema／redaction**：driver `--profile legacy-adoption --legacy-evidence` 不跑 attack matrix 與任何 provider／repository probe，改以 live receipt（applied＋qualified、`legacy_adoption` 的 inventory 與 apply gate digest）與 live quarantine inode 綁定 harness evidence；validate 新增 `--require-legacy-profile`（與 release／canary 互斥），逐項核對 fixture digest、候選綁定、步驟順序、三方 plan SHA、quarantine／rollback／再接手／credential 來源，服務身分必須是 fixture 的 legacy uid／gid；schema profile enum 加入 `legacy-adoption`（providers 必須為空）；redaction scan 的 legacy profile 以 fixture 假 credential 為 needle。
  - **run.sh／workflow**：`run.sh --profile legacy-adoption` 與 release 共用 image、候選驗證與 wheel 安裝，但不把 `/var/lib/cortex` 掛成獨立 volume（quarantine 以 rename 搬移，必須同一檔案系統）並維持 `--network none`；`rc-qualification.yml` 新增 `profile` choice input（預設 `release`，行為不變），run title 帶 profile，legacy artifact 命名為 `rc-qualification-legacy-adoption-<sha>`。
  - **release preflight**：checkout 改 `fetch-depth: 0`；新增 `qualification/release_gate.py`：`legacy-requirement` 以上一個 release tag（release commit 的 parent 可達的最新 `v*` tag；找不到即 fail-closed 視為需要）與 release SHA 的 diff 判斷是否觸及 `paulsha_cortex/trust_root/install/` 或 `qualification/`；需要時以 `select-run --profile legacy-adoption` 找 exact SHA、3 天內、成功的 legacy run 並確認其 artifact 未過期，否則以點名 profile 與變更路徑的錯誤失敗。release RC run 的挑選改為只看 release profile run（舊的無 profile 標題 run 視同 release），PR head 的 RC 檢查也排除 legacy run。
