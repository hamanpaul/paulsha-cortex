第二輪對抗審查修正（各兩條 MAJOR）：

- 驗證 authority 缺席路徑新寫的 `cortex-work-retire-delivered/v2` evidence 對回退相容性：新增測試把 `origin/main`（本票之前）的 `work_actions.py` 載入為獨立 module，直接呼叫其 `_superseded_retire_delivered_body`——確認舊 reader 對本 PR 未改動的 v1 evidence 仍能正常讀回，對新增的 v2 evidence 則是乾淨的 `RuntimeError`（safe fail-closed），不是未攔截例外或資料誤讀；現有程式碼本身已具備此性質，此輪補上可重驗的回歸測試。

第三輪對抗審查修正（BLOCKER＋MAJOR）：
- `work_authority_projection_state()` 補上 `snapshot_path` 參數（預設沿用 canonical durable snapshot，行為不變）：先前完全沒有這個參數，對抗審查建的畸形 snapshot fixture 永遠寫在測試自己的 tmp 路徑，測試斷言實際驅動的是（可能不存在，或執行機器上真正的）canonical snapshot，斷言恆真、驗不到回歸；`tests/test_work_actions.py` 的相依斷言與新增的 `provider-timestamp-unparseable` 情境改用該參數，直接以本次建的畸形 snapshot 驅動。
- `claim.load_work_authority` 對「目標 (repo, work_id) 完全沒有列在 work_items」的 canonical provider 最後健康檢查，補上時間可解析性驗證：抽出共用的 `_validate_canonical_provider_timestamp`（沿用 `_authority_from_canonical_row` 既有的 ISO8601 解析規則，不另寫一套），`_authority_from_canonical_row` 與 `load_work_authority` 兩處共用同一個判斷。先前只檢查 `last_success_at` 是非空字串就視為健康，像 `"not-a-timestamp"` 這種無法解析的畸形值會被誤判為健康，讓 canonical provider 誤判成「根本不存在」而放行 `WorkAuthorityConfirmedAbsent`（registry-only 退休）；現在無法解析一律 `AuthorityValidationError`，fail-closed。

第四輪對抗審查修正（三條 MAJOR）：
- `work_actions.work_authority_projection_state()` 過去一律以 `allow_rate_limited_last_known_good=True` 呼叫 `load_work_authority`，對「真正健康」與「只靠限流 last-known-good 才讀得到」的 snapshot 回傳同一個 `"available"`；但 `execute_work_action()` 對 `_LOCAL_UNBLOCK_ACTIONS`（`abandon`／`retire-delivered`／`reset-reclaim-budget`／`refreeze-base`）以外的動作一律用嚴格（非 LKG）authority 重新驗證，同一份限流 snapshot 會 fail-closed 拒絕，造成 status／work list 對 builder／reviewer run 曝光 `recover-pre-candidate`／`retry-build` 這類正式入口其實會拒絕的動作。改為新增 `"available_last_known_good"` 狀態（先嚴格讀一次，只在因 provider 限流失敗時才再用 LKG 讀一次確認），並新增 `admitted_recovery_actions_under_authority_state()`（與 `execute_work_action` 共用同一份 `_LOCAL_UNBLOCK_ACTIONS`，單一真相）收斂 `manager.workflow_status_entry` 與 monitor work list（`monitor/providers.py`）投影出的 next_actions，只保留正式入口真的會接受的子集（#843 R09 契約）。
- `claim.load_work_authority` 比對 skipped row 時原本只信任 `exc.repo == repo`：row 的 `repo` 欄位本身缺失／畸形（非字串、以 `/`／`~` 開頭、含 `\`）時 `exc.repo` 是 `None`，與任何真實 repo 字串比對恆為 False，即使 `exc.work_id` 與目標完全相符，仍會被判定「與目標無關」而放行到確定缺席分支，誤判 `WorkAuthorityConfirmedAbsent`。改為 `repo`／`work_id` 任一邊「相符」或「因欄位本身畸形而無法判定是否相符」（`None`）都視為「不能排除是目標」，一律 fail-closed 拋出該列原本的錯誤。
- `claim.load_work_authority` 對「目標 (repo, work_id) 完全沒有列在 work_items」的最後健康檢查，過去只檢查 `github:<repo>`；todo-only work item 完全依賴 `repo:<repo>`（本機工作區掃描 provider）供應，該 provider degraded 會讓它從 work_items 消失，卻因為 `github:<repo>` 健康（或根本不存在）被誤判成確定缺席。抽出共用的 `_require_repo_scoped_provider_healthy_if_present()`，對這個 repo 的每一個已存在 provider 條目（至少 `repo:`、`github:`，加上 snapshot 裡任何其他以 `<kind>:<repo>` 形式對應這個 repo 的既有 provider 種類）逐一套用既有的健康／新鮮度規則；條目完全不存在才不擋，維持「provider 根本不存在＝確定缺席」的既有語意。
