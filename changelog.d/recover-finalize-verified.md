### Fixed

- **#1270 `cortex upgrade --recover` 對已驗證、正在服務的 receipt 改為收尾，不再 rollback**（owner 裁決 2026-10-06：cortex 是高信任自主工具，不要停下來等人的機制）：
  - 問題：升級在 verify PASS 之後、`_clear_maintenance_snapshot`／lease marker 清除之前被 SIGKILL 或斷電打斷，或清 snapshot 本身失敗時，下一次升級要求 `--recover`，而 `--recover` 一律 rollback snapshot 綁定的 receipt；activate 之後的 rollback 常常不是 restore-safe，服務因此停住等人工。
  - `recover_upgrade()` 先在 `_recover_command` 用的同一組鎖下（maintenance lease 以 exact plan 接手 stale marker／snapshot，加上該 receipt 的 transaction lock）判斷能否收尾（`_finalize_verified`）：durable plan 的 canonical sha 等於記錄的 plan sha；該次升級綁定的 receipt（snapshot 的 `receipt_path`；只剩 marker 時為 receipt chain 判定、`plan_sha256` 相同的 effective receipt）為 applied＋qualified；`_MAINTENANCE_SERVICES` 三個 service 都 active；Manager／Monitor 的 loaded runtime 與該 receipt 一致（沿用升級 verify 後的 `await_loaded_runtime`／`loaded_runtime_mismatch`，最多等 60 秒穩定）。全部成立時只清 snapshot 與 marker，不 stop／start service、不 rollback，輸出 `{"maintenance_recovered": true, "action": "finalized", ...}`、exit 0；report 的 `result` 改為新增的 `finalized`（加入 report result 的封閉集合），`next_action` 清空，`recovery` 記下收尾的 receipt。
  - 任何一點不成立或無法證明（receipt 不存在／讀不到、不是該 plan 的、未 qualified、service 不 active、loaded runtime 不一致或 status 探測失敗、recovery state 讀不到）一律照舊走 `_recover_command`，lease marker 保留給它接手；輸出多帶 `"action": "rolled-back"` 與 `reason`（如 `receipt-not-qualified: state=… qualified=…`、`services-inactive: …`、`loaded-runtime-mismatch: …`），report 的 `recovery` 記下 action 與原因（rollback 失敗時 `result` 仍為 `halted`）。只剩 marker 時 `_recover_command` 本來就只清 marker、不動 service，該情況標為 `"action": "marker-cleared"`。
  - 證明成立之後，清 snapshot 或 lease marker 失敗一律不落入 rollback（審查修正）：拋出 `_FinalizeFailed`，receipt 與服務不動、剩下的 snapshot／marker 保留，report `result=halted`、`recovery={"action": "finalize-failed", "reason", "receipt"}`，指令以非 0 結束並在 stderr 說明；重跑 `--recover` 會重新證明並收尾。只有證明完成前的失敗才照舊 rollback。
  - `install_cli._recover_command` 新增 keyword-only 的 `emit`（預設 `_emit`），`install trust-root recover` 行為與輸出不變。
  - `trust-root-transactional-install.md`「一般升級」與 §6「手動恢復 `cortex upgrade` 中斷的升級」寫明收尾與 rollback 的判斷條件、輸出的 `action`／`reason` 與 report 欄位；one-command upgrade 設計文件 §7 補上 owner 裁決。
  - 測試：`tests/test_trust_root_upgrade_recover_finalize.py`（18 個）涵蓋 snapshot＋marker、重開機後只剩 snapshot、只剩 marker 時由 receipt chain 證明而收尾，以及未 qualified、不再 applied、loaded runtime 不一致、status 探測失敗、service 不 active、receipt 讀不到、snapshot 指向別的 receipt、apply 前就中斷（走真的 `_recover_command` 恢復服務）、只剩 marker 且生效中的不是該 plan 的 receipt（`marker-cleared`）、durable plan 非 canonical、rollback 失敗時 report 保留原因、證明後清 snapshot 或 marker 失敗（不 rollback、report `finalize-failed`、非 0 結束，重跑後收尾）；並驗證判斷時持有 maintenance／transaction lock、收尾後 `--status` 顯示 idle 且下一次升級不再要求 `--recover`。RC qualification 目前沒有 `--recover` 演練，不受影響。
