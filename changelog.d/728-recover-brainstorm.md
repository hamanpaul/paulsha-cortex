- **#728：`recover-planning` 不再把沒有 brainstorm 背書的 run 推進到 `plan`——recover 的出口狀態與 planning-authority 對帳的入口狀態改為共用同一組前置條件斷言。** 現場（run `workflow-ef40fb2793c5b83818d9`，`brainstorm_required=true`）：define 因環境類 planning 失敗停住，operator 下 `recover-planning` 後逐字回 `action=recovered`／`phase=plan`，下一拍 periodic tick 立刻 `planning-authority-reconciliation-failed`（`ValueError: workflow brainstorm evidence missing`，來源 `manager.resume_workflow_run:planning-authority`），而該 attention 的 `next_actions` 是**空的**——`recover-planning` 只受理 define、`retry-card` 的 phase 表（`registry.RETRY_CARD_PHASE_PERSONA`）不含 plan ⇒ 只剩 abandon 整代重來，對「無人值守跑完一案」是確定性死結。
- **(A)/(B) 裁決：(B)——`recovery_basis: "planning-runtime-retry"` 是「解除封鎖、讓下一拍重跑」，不是「recover 內部已重跑 planning」，修在推進側。** 逐字證據三條：(1) `work_actions._recover_planning_action` 全程沒有任何 planner／runtime 呼叫（無 `runtime_factory`、無 `run_heterogeneous_brainstorm`，不寫 `gate_refs`／`planning_authority`／`planning_source_revision`），它只讀失敗 evidence、落稽核紀錄、清 `needs_human`／`blocked` 兩個 facet；(2) 全庫唯一產生 brainstorm gate evidence 的路徑是 `manager.apply_workflow_action` 的 define 段，且 `gate_refs=result.gate_refs.as_tuple()` 與 `current_phase="plan"` 在**同一次** registry 原子寫入內完成；(3) 那條路徑的入口守衛逐字是 `if run.current_phase not in {"claim", "define"}: return … "already-claimed"`，`work_bridge.start_canonical_workflow` 另有 `if existing_run.current_phase != "define": return existing_run` 短路。⇒ 推進到 `plan` 不是「前進」，是**永久關掉**產生背書的唯一入口。票上「artifact 已發佈」的讀法（傾向 (A)）被 (1) 否證：那句訊息是對帳函式的固定文案，不是 recover 真的發佈過東西的證據。
- **前置條件抬成單一導出點 `workflow.brainstorm_authority_bound(run, *, phase=None)`**，由 `manager._validated_brainstorm_planning_authority`（對帳側）與 `work_actions._recover_planning_action`（recover 側）**共用同一個函式物件**；recover 傳入它**打算**寫進去的 phase，問的是「我即將造出來的狀態是不是合法入口狀態」，答案是否就退回 `define`，出口狀態因此在結構上不可能不是合法入口狀態。判準兩條：run 還在 `PLANNING_PUBLICATION_PENDING_PHASES`（＝`{"claim","define"}`，與上述兩個守衛的字面集合同一份）內時無條件成立；離開之後 `brainstorm_required` 的 run 必須帶著**它自己的** brainstorm gate ref。
- **順帶修掉一個範圍更大的既有 wedge**：`brainstorm_required` 且無背書的 run 停在 `define`／`needs_human` 是三條 planning 失敗路徑的**正常**產物，而 operator 只要下一次 `cortex work resume`（`operator_resume=True`）就會在 **`define`** 撞上同一句 `workflow brainstorm evidence missing`。實測未修改的 main：`define` 與 `plan` 兩個 phase 都回 `planning-authority-reconciliation-failed` ＋ `next_actions: []`。只修 recover 側會把死結從 `plan` 搬到 `define`，因此前置條件必須是 phase-aware 的。
- **`planning-authority-reconciliation-failed` 不得再出現 `next_actions: []`。** `needs_human` run 的基礎合法動作集合抬成 `claim.needs_human_next_actions()`（`abandon` 永遠合法 ⇒ 回傳值不可能為空；`recover-planning` 只在「停在 define 的環境類 planning 失敗」浮現，與 `_recover_planning_action` 自身的前置驗同一組判準），由 `claim._resume_decision` 與 `manager.workflow_status_entry`（`cortex status` 的 attention 投影）共用。修正前後者**只**由 `work_actions._phase_recovery_actions` 導出，而它只涵蓋 build／verify／review 三個 phase，plan 的 run 因此永遠拿到 `[]`；現在 `_phase_recovery_actions` 退回原本職責——**補**那些要看 job 層事實才判定得出來的動作（`regenerate-gates`／`retry-card`）。曝光面算不出 job 層動作時（registry 讀取失敗）仍保底回 `["abandon"]`。
- **回應面**：`recover-planning` 的回傳新增 `recovered_phase`，operator 不必翻 evidence 檔就看得到這次 recover 把 run 留在哪裡；recovery evidence 的 `recovered_phase` 隨之誠實記錄，不再寫死 `plan`。
