- transactional installer 的 legacy adoption 進入 plan 階段（#1122，PR-3）：host overlay、`legacy_policy` 語意、disposition 推導與 `legacy-quarantine` step；apply 暫時一律拒收 legacy plan。
  - **`plan --host-overlay O`**：套用 PR-2 已驗證的 allowlist overlay（帳號 uid／gid、egress home、`operator_account`、`external_reader_account`、`providers.builder`、`legacy_adoption`），plan 頂層記錄 `host_overlay_sha256`（overlay 去掉 `legacy_adoption` 後的 digest，與 inventory 記錄的相同，之後沿用同一份 overlay 升級時不變）。沒有 overlay 時 plan 逐位元組不變（release config 黃金 digest 回歸測試）；overlay-only 的 plan 照常可 apply。
  - **`legacy_policy` 語意**：`reject` 帶 `legacy_adoption` 區塊或 `--legacy-inventory` 一律 `InstallPlanError`；`quarantine` 沒有區塊時與現行完全相同；`quarantine`＋區塊必須搭配 `--legacy-inventory`，反之亦然。區塊只能由 host overlay 提供：`inventory_sha256`、`quarantine_root`（必填），選填 `census_exceptions`（`{path, principal}`）與 `quarantine_paths`（operator 審核後明示移入 quarantine 的物件，是 `unclassified` 唯一的解法）。
  - **`plan --legacy-inventory P` 綁定**：驗證 inventory schema 與自證 digest、區塊的 `inventory_sha256`、以同一份 config／overlay／bundle 重算的 scope digest、inventory 擷取時的 overlay 記錄，以及本機 machine-id 的 host binding；任一不符即停。
  - **disposition 推導（依 design D3，「必要子集」）**：帳號逐欄（uid／gid／home／shell、同名 group 的 gid 與成員、supplementary、密碼鎖定、uid／gid 持有者）完全符合 overlay → `adopt`，任一不符或 id 被其他身分持有 → plan 失敗並點名持有者（不支援 remap），不存在且 id 未被占用 → 照常建立；受管目錄型別正確 → `adopt-in-place`，型別錯誤 → 失敗；job worktree pool（`worktree`、`gate-worktree`）、`toolchain/bin` 整個目錄、source repository、受管 generated 檔、不符的受管 symlink、credential 類受管路徑 → `quarantine-then-create`；完全相符（target 與 owner）的受管 symlink → `adopt`；venv active link 是實體目錄 → `quarantine`、是 symlink → 失敗；版本化 toolchain 路徑或 venv slot 已存在 → 失敗；state 頂層未宣告項目、受管目錄內未列管子目錄與暫存／備份殘留、installer 未產生的權威面物件（drop-in、`.env.bak-*` 等）、credential 類物件、deploy root 舊備份（`venv.*`、`operator-backups`）與已由 launcher 取代的 #568 `agy-reviewer-settings.json`／drop-in → `quarantine`；指向受管 unit 的 `*.wants` 啟用 symlink → 由對應 `systemd:enable:*` step `adopt`。其他（含特殊檔案型別）→ `unclassified`，plan 失敗並一次列出全部原因。受 quarantine 祖先涵蓋的物件隨祖先一次搬移，不另建 step。census 為 `unstable`、可寫路徑不在 plan 宣告可寫資產或 `census_exceptions` 內、cortex unit 從 systemd root 以外載入或有 quarantine 涵蓋不到的 cortex drop-in、quarantine 目標是 mountpoint、`quarantine_root` 與 inventory scope 重疊 → 皆失敗。
  - **plan 頂層 `legacy_adoption` 區塊**：`schema_version`、`inventory_sha256`、`scope_sha256`、`host_binding_sha256`、`host_overlay_sha256`、`quarantine_root`、`adopted {step_id: row_sha256}`、`quarantine`（path／disposition／reason／row_sha256／covers）、`census_exceptions`、`summary`，全部納入 `plan_sha256` 與 canonical receipt path。
  - **`legacy-quarantine` step**：`legacy-quarantine:<path>`，destination 為 `<quarantine_root>/<inventory_sha 前 16 碼>/root/<原絕對路徑>`，`expected` 帶 type／uid／gid／mode／dev／ino 與 `sha256` 或 `link_target`（credential 只綁 metadata），`row_sha256`、`operations: [snapshot, rename-noreplace]`、`rollback_policy: restore`。排在父目錄的受管 step 之後（父目錄不受管時緊接帳號 step）、同路徑或其下任何 step 之前；`_assert_managed_parent_topology` 與 apply plan schema 驗證認得此 kind，並逐項驗證區塊與 step 的一致性（scope、overlay、destination、row digest、adopted step、quarantine 與 step 的雙射）。
  - **apply 暫不支援**：`validate_apply_plan`（apply、lease、lease-release、recover 共用）驗證 legacy plan 的結構後明確拒收（legacy apply 尚未實作），不會建立 receipt 或 maintenance snapshot。
