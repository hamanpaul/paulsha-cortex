- **#727：codex planner safe probe 永遠 not-ready——`-o` 的落點是第二份決定、串流備援從來沒能用過、而 diagnostic 只有 `ValueError` 五個字。** 三層疊在一起的後果是**不可辨識性**：「落檔那條斷了」與「模型什麼都沒吐」在 operator 眼裡是同一個字串，這正是本票拖了四輪派工的原因。0820 實機在**真實加固面複本**（`psc_run_under cortex-reviewer-job-jit`，`permgen.unit_replica_properties()` 全量導出 **52 條 property**）下跑一次 `_planning_argv()` 產出的 production argv：rc=0，`agent_message` 逐字等於 `_probe_identity` 的 `expected`——**模型端完全正常**，失敗全部在我們自己的解析路徑上。同一份串流餵給 `origin/main` 逐字得到 `ready=False reason=safe-probe-failed diagnostic='ValueError'`，餵給本 PR 得到 `ready=True`（該串流逐位元組存成 `tests/fixtures/codex-planner-probe-0820.jsonl`，含開頭那筆 `item.type=error`）。
- **(1) `-o` 落點由單一來源機械導出——`#714` 缺陷 2 的規則終於涵蓋 planning 這條路。** `planning_runtime._planning_argv()` 原本自己組 `Path(temp_dir)/"last.json"`，而 job 模式下 `temp_dir` 被硬填 `"/tmp"` ⇒ 落在 unit 的 `PrivateTmp=yes` 私有 /tmp：job 寫得進去、**Manager 讀不到** ⇒ 第二候選恆為 `None`。design 的 D-j／R-2 把這件事記成「已知退步」，但那不是結構限制——它是**第二份落點決定**，而 #714 早就替 builder lane 回答過同一個問題。修法：`last_message_path` 成為 `_planning_argv()` 的**必填關鍵字參數**（沒有預設值——留一個預設值等於把那份決定藏起來，漏傳的症狀因此是 `TypeError` 而不是三個月後實機上的一次錯位），兩個 invoker 各自經 `planning_last_message_path()` ＝ `job_workspace.job_last_message_path()` 交出答案。job 模式落在 `<planning-logs>/<instance>/planning.last.json`，direct 模式落在 `<一次性 tempdir>/planning.last.json`。**零部署動作**：實機 `getfacl` 逐字 `default:user:cortex-reviewer-planner:-wx`，而該路徑嚴格落在模板 unit 既有的 `ReadWritePaths=/var/lib/cortex/coordinator/review-verdicts` 之內（0820 由 `unit-replica` 全量導出逐字確認）。那一格由 **Manager 預建**（`spool_slot.preseed_job_writable_file()`，mode `0620`，與 job log 檔逐字相同的論證與同一份實作）⇒ job 寫得進去、Manager 讀得回來，**R-2 在 planning 這條路上解除**。`JobPlanningInvoker._dispatch()` 另對 `run()` 傳下來的落點與自己導出的那一份做**逐字比對**，漂移即 fail-closed（比照 `launcher.launch()` 對 #714 那一格做的事）。
- **(2) 串流備援要真的能用——`_extract_stream_json()`，由尾端往回找。** `_find_json_object()` 的頂層語意是嚴格的「整串剛好是一個 JSON 物件」（#670 刻意收窄），而 codex 的 `--json` 是 **JSONL** ⇒ 整串 `json.loads` 必敗 ⇒ 候選迴圈全滅 ⇒ `ValueError: planning launcher returned no JSON object`。**串流備援名義上存在、實際上從來沒有能用過**，因此落檔一旦斷掉就無路可退。新增的抽取比照 `manager._extract_terminal_json()`：**由尾端往回找**，先看到 `turn.completed`（沒有文字欄位、自然跳過）再看到 `agent_message`，開頭那筆 error item 因此**結構上**不可能遮住輸出本體——不是靠一條「跳過 error」的特例。它排在既有兩個候選**之後**，因此「兩者皆有」時第二輸出仍然優先、既有行為逐字不變；頂層那條嚴格語意一個位元組都沒放寬（帶前言散文的輸出照樣 fail-closed）。**落檔那條刻意保留**：兩條都在才有可辨識性。⚠️ **錯誤事件一律零產出**：codex 的錯誤訊息常內嵌 JSON（0820 實機逐字 `unexpected status 400 Bad Request: {"detail":"…"}`），少了這條守衛，`allow_partial=True` 會把 `{"detail":…}` 抽出來當成「模型輸出本體」，一次硬失敗變成一份看起來像資料的錯誤資料（下游只會報 `identity-mismatch`，比 `ValueError` 更誤導）——與 `manager._unwrap_structured_output` 拒絕寬鬆解析是同一條理由。
- **(3) `safe-probe-failed`／`models-probe-failed` 落有界診斷。** `probe_exception_diagnostic()` 把型別名**錨在第 0 個 token**，後面接三格：`rc=` ／ `stdout=<節錄>` ／ `last_message=<路徑>|<狀態>`。第三格是關鍵——它逐字回答「`-o` 那一格到底寫進去了沒」，而 `<absent>`／`bytes=N`／`<unresolved:PermissionError>` 是**三件不同的事**。全體上限 `PLANNING_DIAGNOSTIC_LIMIT = 2000`（＝`manager.RETRY_CONTEXT_EVIDENCE_LIMIT`，兩者相等由測試釘住——`model_identities` 不 import `manager`，反向會成環）。`classify_probe_failure()` 改為只看第 0 個 token，**分級輸入因此逐字不變**——上下文加不加、加多少，對三分結果一個位元都不影響，也就沒有任何 probe 因為診斷變豐富而從 not-ready 變成 ready。**型別名絕不換掉**：包一層自訂子類會讓 `type(exc).__name__` 變成不在兩張表上的新名字 ⇒ 三分整組落 `unclassified`，因此原例外**原封往上拋**、只多掛一格唯讀屬性（`attach_probe_diagnostic()`）。agy 那一格同理：`probe_agy_capability` 原本對 `PlanningJobError` 只取 `type(exc).__name__`，實機 0819 逐字只剩 `PlanningJobError` 六個字，而 rc／unit／profile／binary／version／seccomp 全都好端端待在 `.detail` 裡。**票 A 的邊界沒有放寬**：只取 stdout，stderr 一個位元組都不取（有測試釘住診斷不得含 stderr 內容）。
- **順帶（同因，小）：probe cache 的憑證指紋曾經對 operator 說假話。** `_stat_marker()` 把**所有** `OSError` 都收成 `<absent>`，於是實機逐字 `fp.executor_credential = …/.claude/.credentials.json|<absent>` **而那個檔已經存在**（`.claude` → `cache/claude` symlink，`cache/` 是 `0700 cortex-reviewer-planner`，Manager 在 traverse 那一步拿 `EACCES`）。本模組開頭早就寫下 `<absent>`（查得到答案，答案是沒有這個檔）與 `<unresolved:…>`（連查都查不動）的分工，只是實作沒有兌現。⚠️ **這只修掉假話，沒有修掉那一格的真正缺陷**：兩個標記在同一個部署上都是**恆定**的 ⇒ **憑證輪替仍然不會讓 probe cache 失效**。真正的修法要換一個 Manager 看得見的失效訊號，或讓指紋由看得到那一格的身分算（＝每次算指紋多派一個降權 job，在 planning 的熱路徑上）——兩條都擴散到部署面，本票只記錄不硬做。
- **⚠️ 一併更正一條量測方法上的陷阱（本 PR 自己踩過，記下來給下一次）**：`systemd-run --property=… <bare command>` 解析執行檔用的是 **systemd 自己的內建 path**，不是複本裡那條 `--property=Environment=PATH=`。因此 `psc_run_under cortex-reviewer-job-jit codex --version` 逐字回 `codex-cli 0.42.0`（系統層那份），而 production 的 `job_shim` 走 `os.execvpe(command[0], command, job_env)`、以 **job env 的 PATH** 解析，實際跑的是 `/opt/cortex/toolchain/bin/codex` ＝ **0.147.0**。兩者差一個大版本，而 0.42.0 的 `codex exec` **沒有 `-o` 短旗標**（只有 `--output-last-message`）也**不支援 `gpt-5.3-codex-spark`**（API 逐字回 400 `requires a newer version of Codex`）——本 PR 初版因此差點把一個不存在的旗標缺陷寫進 argv。**複本必須連「production 用什麼解析執行檔」也一起複製**；量真實加固面下的 executor 行為時，命令要給**絕對路徑**（或經 shell 以複本的 PATH 解析），否則量到的是另一支二進位。這是 #679「複本比 production 多」的鏡像：複本比 production **舊**。
