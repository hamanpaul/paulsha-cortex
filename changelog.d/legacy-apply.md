- transactional installer 的 legacy adoption 進入 apply 階段（#1122，PR-4）：apply 前重新擷取 inventory、quarantine backend、receipt 的 legacy provenance、rollback 回到 legacy 並證明；移除 apply／lease／recover 對 legacy plan 的暫時拒收。
  - **`apply --legacy-inventory P`**：plan 帶 `legacy_adoption` 區塊時必填、沒有區塊時拒收，與 `--prior-receipt` 互斥（CLI 在取得 lock、建立 receipt 之前即拒絕）。inventory 檔必須就是 plan 綁定的那一份（自證 digest、scope、host binding、overlay 記錄、每個 adopted row digest 與每個 `legacy-quarantine` step 的 expected 都要對得上）。
  - **apply gate（第一個 mutation 之前）**：在 transaction lock 內、lease 停服務後、receipt 離開 `planned`（或已證明的 `rolled-back`）之前，以 plan scope 重新擷取 inventory，穩定欄位 digest、host binding、scope 必須等於 plan；census 不得有 `unstable` 或新的可寫例外（點名 principal 與路徑）；in-flight job（含無法證明的 durable 計數）、未停的三個 service、任何 active 的 `cortex*` unit 或 job template instance 皆失敗。失敗時 receipt 維持 `planned`、journal 為空。通過後 receipt 在轉為 `applying` 的同一次 checkpoint 寫入頂層 `legacy_adoption`（`inventory_sha256`、`inventory_path`、`host_binding_sha256`、`quarantine_root`、`apply_inventory_sha256`）；`applying`／`applied` 的 replay 依賴這筆紀錄，`rollback-blocked` 等狀態拒絕。
  - **preflight 與事前掃描**：`adopted` 帳號只在 inventory row 與現況逐欄相等（passwd、同名 group、supplementary、密碼鎖定、uid／gid 持有者）時補上 provenance，所有 collision 檢查照舊先行；symlink 與過大既有檔檢查對 pending quarantine 涵蓋的路徑與 quarantine step 本身豁免；被涵蓋的受管 step 視為 fresh，不對 legacy 物件呼叫 `inspect_step`（venv active link 亦同）；每個 quarantine step 事前確認來源仍是 inventory 的 inode／metadata／digest、destination 不存在、destination 鏈安全且與來源同一檔案系統。接手物件逐 step 以 live 重算的 inventory row digest 證明。
  - **quarantine backend**：prepared entry（`prior` 為 inventory 的 lstat＋dev／ino、`quarantine_authority` 為來源 dev／ino 與 destination）先落盤，再建 root-only 0700 destination 父鏈（每個 component 以 `O_NOFOLLOW` 相對開啟；quarantine root 以上的祖先須 root 擁有且他人不可寫，root 以下須 root 0700），檢查同 `st_dev`（不同或 `EXDEV` 即 fail-closed，無 copy fallback），以 ctypes 直呼 `renameat2(RENAME_NOREPLACE)`（未知架構或 `ENOSYS`／`EINVAL` 即拒絕），fsync 兩邊父目錄後才標 completed。replay：來源已不在且 destination 為記錄的 inode → 直接 completed；來源仍是未變的 legacy 物件 → 重做；其他 → drift。
  - **quarantine 搬移的 TOCTOU 防護**：prepared entry 的 `quarantine_authority` 另綁來源父目錄的 dev／ino（有 inventory row 的父目錄須與 row 相符）；backend 只憑 prepared entry 搬移（`quarantine_step`，`apply_step` 對此 kind 一律拒絕），以 `O_PATH|O_NOFOLLOW` 逐層開啟來源父目錄並驗證其 inode，所有 no-follow 檢查與 `renameat2` 都在同一個 dirfd 上；rename 後立即在 destination 驗證 type／owner／mode／dev／ino 與 digest 或 link target，不符即以 `RENAME_NOREPLACE` 搬回原處並以 drift 失敗（entry 不標 completed）；若搬回也被拒（原位又被佔），entry 記錄 `quarantine_unexpected`（destination 內的非預期物件），replay 一律拒絕、rollback 永不把它當 legacy 搬回且維持 rollback-blocked、`restore_safe=false`。replay 只在 destination 與 inventory 完全相符時補標 completed。
  - **adopt-in-place**：沿用既有非遞迴 `replacing` metadata replacement（先 checkpoint dev／ino），中斷後先還原再重做。
  - **receipt provenance**：接手的 entry 帶 `adoption: {source: "legacy-inventory", row_sha256}`，永不以 `adopted_from_receipt` 冒充；provenance 判斷收斂為 `_entry_has_adoption_provenance(entry, plan)`。`InstallReceipt.load` 驗證 `legacy_adoption` 紀錄與 embedded plan 一致、有 journal 的 legacy receipt 必須有紀錄、`adoption` 只能出現在 plan `adopted` 且 digest 相符的 step、quarantine entry 的 `prior`／`quarantine_authority` 與 step 完全一致。
  - **rollback**：反向 journal 以 `RENAME_NOREPLACE` 搬回 quarantine 物件（原位被佔或 destination 不是記錄的 inode → retained drift，物件留在 quarantine），systemd root 下的 quarantine 物件搬回後納入最後一次 `daemon-reload`；`list_unknown_state` 把已搬回（inode 相符）的 quarantine 來源視為受管路徑。最後以 plan scope 重新擷取，穩定欄位 digest 等於原值才回報 `legacy_restored=true`，否則記 retained drift、`restore_safe=false`、服務維持停止；`rollback` 與 `recover` 都做這個證明。
  - **以 adoption receipt 升級**：`validate_prior_receipt_handoff` 要求 prior adoption receipt 帶 apply gate 紀錄，`_prior_account_provenance`／`_prior_step_provenance` 經同一個 helper 接受 legacy adoption row；同一份持久化 overlay 產生的下一版 plan 可帶 `--prior-receipt` 升級。
  - **plan 驗證補強**：`quarantine_root` 不得與 canonical receipt 目錄重疊。
  - 沒有 legacy 區塊的 plan：apply、replay、prior-receipt 升級與 rollback 的 receipt 內容、backend 呼叫序列與 rollback 報告與改動前逐位元組相同（以基底程式錄製的黃金 digest 回歸測試）。purge（tasks 3.8）不在本 PR。
